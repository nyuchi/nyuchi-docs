**Weather is infrastructure, so it belongs to Nyuchi** (owner direction, 2026-10-29). Nyuchi Web Services builds and runs it; Mukoko Weather is the consumer product on top of it, alongside the other apps and partners that read it. Where this page says "the weather repo" it means `mukoko-dev/mukoko-weather`, which still sits under the Mukoko organisation. Whether it moves is an open decision (section 7).

The one goal behind everything we build: **a person anywhere on Earth, and above all in Africa, opens Mukoko Weather and learns what the weather means for what they need to do today.**

Every `/loop` we run is an overarching objective that moves that goal. This file is the source for those loops: what each objective is, what moves it, who it helps, what is safe to do unattended, and what needs the owner.

Sources: the repo docs (`CLAUDE.md`, `README.md`, `workers/README.md`, `releases/`), the open `mukoko-dev/mukoko-weather` issues as of 2026-10-29, `mukoko-api`, `mukoko-weather-mobile` and `nyuchi-servers-api`. "Decided, not built" is said wherever that is the case. Nothing here was measured in production; metrics marked _not yet measured_ have no baseline.

## 2. Rules that hold for every loop

These are owner decisions already recorded in the repos. A loop that breaks one has failed.

1. **Backend is Rust Workers only.** Vercel is frontend only. `api/py` is frozen: no new features there, only ports out of it.
2. **A domain refers to another by id.** Geography is Places. Weather keeps no countries, provinces or regions of its own (#359). Agriculture is its own domain (`agriconnect`); weather adds no agriculture data store.
3. **Standards, not inventions.** CF standard names with units declared once, ISO 8601 with the place's IANA zone, ISO 3166 codes, WIGOS on stations, WMO 4677 weather codes, schema.org with JSON-LD.
4. **The coordinate is the identity, the name is cosmetic** (#317). No valid coordinate dead-ends.
5. **Tomorrow.io enriches, never carries the baseline** (#246).
6. **Never invent data.** A place with no crop calendar gets a derived window that names no crops. A provider outage serves the seasonal estimate, labelled.
7. **Errors are isolated per section.** A broken chart never takes down the page.
8. **Nothing is published, merged, deployed or released by a loop** without the owner's approval. The merge gate is: complete, CI green, verified at runtime, `/code-review` clean.
9. **Secrets, keys and credential status never go in files or public issues.**
10. **Stations are registered on the Nyuchi API** (owner direction, 2026-10-29), not on a weather-only endpoint, so a station has one registration and one id wherever it is used.
11. **Playbooks live here**, on docs.nyuchi.com, in `nyuchi/nyuchi-docs`. A copy in an app repo goes stale; link to this page instead.

## 4. The objectives (one `/loop` each)

Order is priority. Objectives 1 to 3 are the foundation and unblock the rest. Do not start a new objective's loop while an earlier one has an unresolved owner blocker that it depends on.

### Objective 1: Any place on Earth renders real weather

- **Entity:** Nyuchi. **Refs:** #317, #302, #273, #359.
- **Why:** A farmer, a pilot or a traveller who searches for a place and gets a dead end never comes back. Search, GPS and plain-name URLs now resolve worldwide (v0.12.0), but the location pipeline is still described for Africa first (#273) and holds its own location list (#359).
- **Metric moved:** share of searches and GPS fixes that end on a rendered weather page; 404 rate on real place names; search-to-page-view rate. _Not yet measured_: add the event first (see Objective 6 loop step).
- **Story to tell:** someone in Koh Samui, Gweru or a farm paddock with nothing mapped typed their place and got weather for exactly there.
- **Loop does:**
  1. Probe a fixed list of 50 places (Africa-heavy: rural Zimbabwe, Sahel, Indian Ocean islands; plus world cities, open water, polar) through search, GPS coordinates and bare-name URLs; record pass or fail.
  2. Fix failures in `workers/places` and `weather-core::resolve` with a native cargo test per fix.
  3. Replace the app's own location list with Places ids as #359 requires (read country and region from Places, never store them here).
- **Done when:** all 50 probes pass, and a test pins each past failure.
- **Safe now:** probes, native tests, fixes inside the Workers. **Needs sign-off:** any change to the Places schema or to what the Nyuchi API stores (platform-owned).

### Objective 2: One backend, Rust Workers, Python deleted

- **Entity:** Nyuchi. **Refs:** #333, #148, #174, #351, #297.
- **Why:** Two backends doubles the failure surface and keeps weather tied to Vercel. The owner decided Rust-only. Remaining Python routes are listed in #333 in four batches.
- **Metric moved:** share of app calls served by Workers (target 100%); p95 page-load; error rate on the page-load path; cold-start failures on the seed fallback.
- **Story to tell:** weather loads the same speed on a slow phone in Bulawayo as in Singapore, because the answer comes from the nearest edge, not a serverless cold start.
- **Loop does:** one batch per run, in the #333 order (page-load routes, then agriculture/model-grid/profile, then reference data, then writes). Per route: same JSON as the Python, shared fixtures between Python and Rust tests, same caching, breakers and budgets. Then repoint with no `/api/py` fallback.
- **Done when:** `api/py`, its tests and the Vercel rewrites are deleted, and `/api/py` has zero call sites in `src/`.
- **Safe now:** porting and tests, one batch at a time (disk is about 1.5 GB: share one cargo target dir). **Needs sign-off:** every deploy (`workers-deploy.yml`, behind the `workers-production` Environment), and the release blockers in #351 (Mongo bridge Worker, Atlas read-write user, index repairs). Those are owner steps.

### Objective 3: Weather stops being a silo

- **Entity:** both. **Refs:** #359, #150, #277, #265, #291.
- **Why:** The owner's order of 2026-10-28. Stations store `airTemperatureCelsius`-style names, not CF names; locations are not Places ids; weather has an agriculture endpoint that now belongs to another domain.
- **Metric moved:** none for users directly. It protects every later metric: fewer duplicate records, and other Nyuchi products can read weather without translation. Measure as count of weather-owned geography/agriculture collections (target 0).
- **Loop does:** an audit-then-migrate cycle against #359's change list: Places id on locations and stations; WIGOS id where a station has one; CF standard names with the unit declared once; ISO 8601 plus IANA zone; no stored countries or provinces; point `/agriculture` consumers at `agriconnect` when it serves them.
- **Done when:** a drift check (the `platform-architect` agent pattern) finds no weather-owned copy of geography or agriculture data.
- **Safe now:** read-only audit, renames behind adapters with tests. **Needs sign-off:** any data migration on the shared cluster, and anything that touches `data-infra`.
- **What `data-infra` already says (#90, read 2026-10-29; comments dated 2026-10-28; the owner's mandatory-and-urgent note is tracked in `data-infra#122`):** weather has no module in the platform model (`schemas/model/`), so nothing checks it. Findings: ObjectId `_id` instead of UUID strings; free-text country and province on stations; two metric names per quantity (`temperatureCelsius` and `airTemperatureCelsius`, and three more pairs); daily values keyed by an instant instead of an ISO date plus IANA zone; `regions` boxes not in GeoJSON `bbox` order. Planned sequence: a `weather.yaml` model PR (no data touched), then a station-to-place match report, then a backfill that needs your yes. Unmatched stations are listed, not guessed. The sibling issues are `nyuchi-api#397` (the `/v1/weather` router, which filters stations by free-text country and province) and an unfiled audit of the mobile app. The agriculture domain was added in `data-infra#117` (merged 2026-10-28) with no data model yet; `nyuchi/agriconnect` is an empty repo (a heading in its README).
- **Loop order for this objective:** (1) review the `weather.yaml` model PR when it lands, (2) make new code in this repo write the model's names only, behind adapters, (3) wait for the match report before any backfill.

The agriculture links to `knowledge.topics` are blocked: two inserts failed validation and nothing exposes the validator. That is the first gap in the "Tooling gaps" section below. **Correction (owner, 2026-10-29): one domain, one kind of data.** The first agriculture model in `data-infra#138` wrongly carried weather and geography records (a WIS2 dataset entry, an OCHA boundary entry, a `registry-loaded` status). Those are removed from the agriculture model: agriculture holds crop, yield, production, food-security and rainfall-for-farming data only. ### 3c. External sources: convert at the edge, store our schema

The rule: **we never adopt an external API's schema.** Every feed (WIS2 from the Zimbabwe Meteorological Services Department, SAAOPA WX-CoPilot, Open-Meteo, Tomorrow.io, AWC) goes through a transformation layer that outputs our standard model, and only that is stored or served.

- Names are CF standard names (`air_temperature`, `relative_humidity`, `surface_air_pressure`, `air_pressure_at_mean_sea_level`, `wind_speed`, `wind_speed_of_gust`, `wind_from_direction`, `dew_point_temperature`, `precipitation_amount`). One name per quantity.
- Units are declared once, in SI and UCUM (`Cel`, `%`, `hPa`, `m/s`, `deg`, `mm`). Knots and km/h are display formatting, never storage.
- Identifiers are WIGOS ids for stations, ISO 3166 for countries, ISO 8601 / RFC 3339 for times with an IANA zone. Provenance and licence travel with each value.
- The standards register has WMO station ids, WMO 4677 and CF. It does not yet list UCUM, the WIS2 / OGC API Features profile, or OCHA P-codes. Proposing them is a small change to `standards/register.yaml` in `data-infra`.
- Why: it is what lets us publish and contribute to global models. If our storage mirrors one provider, we are locked to that provider.

The first parsers (`mukoko-dev/mukoko-weather#362`) emit the app's older metric names, in km/h. That is being reworked to this rule before anything calls a feed.

### Objective 4: Forecasts people can trust in Africa

- **Entity:** both. Free for everyone; the research is Bundu's. **Refs:** #246, #247, #245, #268, #280, and the station fleet.
- **Why:** Global models are weakest where our users are. The blend and fallback chain exist, but weights are a starting guess, nothing is verified against observations, history only recently resumed after stopping in July 2026 (#245), and we have one station.
- **Metric moved:** forecast error against observations per region (temperature and rain, 24 h and 48 h); number of validated stations; days of continuous history per place. _Not yet measured_: the verification docs are captured but no job joins them to observations.
- **Story to tell:** a school put a rain gauge and thermometer in the ground, typed in a reading, and the forecast for their village got better.
- **Loop does:**
  1. Build the verification join (captured forecasts against StationKit observations, else ERA5) and report error by region.
  2. Propose per-region weights into `modelBlendConfig` for the owner to approve.
  3. Prototype CHIRPS and TAMSAT point extraction for rainfall anomaly ("is this season drier than usual?"), as scoped in #247.
  4. Keep history healthy: assert one doc per place per day.
- **Done when:** a weekly error report exists per region and weights change only from that report.
- **Safe now:** analysis, reports, prototypes, tests. **Needs sign-off:** weight changes, ingest jobs that add Cloudflare cost, and the licensing question below.
- **StationKit is the load-bearing piece of this objective.** See section 4a.
- **Licensing blocker:** Open-Meteo's free API is non-commercial. Fine while we run at break-even and free, but any paid tier, or the developer API sold to businesses, needs the commercial plan, the self-hosted instance (#280, code ready, not deployed), or direct ECMWF/GFS/ICON ingestion. Decide before Objective 7.

### 4a. StationKit (`nyuchi/stationkit`)

StationKit is the station network that makes the loop "my station improves your forecast, your station improves mine" true, and it is the only way weather gets ground truth in places the models model badly.

**Where the pieces live (read 2026-10-29):**

- **Station console:** `nyuchi/stationkit` `staging` already holds it (`console/`, Astro 7 on Cloudflare Workers, deploy workflow, merged 2026-10-11 to 2026-10-21). `main` does not have it yet, which is why `main`'s README still says no code has landed. The old Next.js copy is `station-console/` in this repo. The new console talks only to `api.nyuchi.com`, where `POST /v1/stations` and the other station routes are not built (live probe 2026-10-11), so it answers "not live yet". The live ingest is the weather repo's stations Worker at `weather-ingest.nyuchi.com`. So the move is mostly done in code, and what remains is: release `staging` to `main`, build the station routes on the Nyuchi API (or point the console at the existing Worker), then delete `station-console/` here.
- **Product page and pilot signup:** `bundu-labs/marketing`, `apps/nyuchi/src/pages/stationkit/{index,signup}.astro` (Astro monorepo with the nyuchi.com, bundu.org and mukoko.com sites). The signup form posts to Formspree, not to any station-registration API, so a pilot signup does not create a station.

**What exists (read 2026-10-29):**

- The repo is a README and a licence. There is **no firmware and no hardware design**. The device is specification only: ESP32-C3, ESP-IDF, solar plus 18650, 5-minute reads, hourly batches of 12, about 48 h of flash buffer. The README says the figures are targets, not measurements, and that no hardware has been built from the repo.
- The design record is four draft issues: #3 hardware, #4 firmware, #5 API contract, #6 data schema and QC. All carry `TODO` markers.
- What runs in production is elsewhere: the pilot signup on nyuchi.com, the console at `weatherstations.nyuchi.com`, and the ingest and QC pipeline in this repo (`/api/py/stations/*`, being ported to `workers/stations`). Any consumer station can already push through the Wunderground or Ecowitt "custom upload" protocols, and analog stations can submit by hand. One station is active: Nyuchi Africa HQ, Harare.

**Contract drift to resolve before any firmware is written** (nothing downstream can be built until it settles, as the README says):

| Topic          | StationKit draft (#5, #6)                                          | What this repo runs today                                                         | Platform rule (#359)                    |
| -------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------- | --------------------------------------- |
| Endpoint       | `POST /v1/stations/{stationId}/readings`, bearer token per station | WU `GET` and Ecowitt `POST` with `PASSKEY=<stationId>:<ingestKey>`; manual `POST` | Not decided                             |
| Field names    | `temperatureC`, `windSpeedMs`, `rainfallMm`, `pressureHpa`         | `airTemperatureCelsius`, `windSpeedKph`, `precipitationMillimeters`               | CF standard names, unit declared once   |
| Wind unit      | m/s                                                                | km/h                                                                              | CF `wind_speed` is m/s                  |
| QC             | Range, spike, cross-check against satellite data                   | Inline range check only; no spike or cross-validation                             | Not decided                             |
| Identity       | Station id and key                                                 | Station id and key                                                                | Places id plus WIGOS id where it exists |
| Publish onward | To Open-Meteo                                                      | Not found in this repo                                                            | Not decided                             |

Three name sets for the same quantities is the silo problem in miniature. The draft's m/s is the one that matches CF; the live code's km/h does not.

**Decision (owner, 2026-10-29): stations are registered on the Nyuchi API.** That settles the open question about the console's backend. The console in `nyuchi/stationkit` already targets `api.nyuchi.com`; what is missing is the API side. In `nyuchi/nyuchi-api`, `gateway/routers/weather.py` has only read routes (`GET /v1/weather/stations`, `/stations/{id}`, `/stations/{id}/observations`, `/observations`, `/alerts`, `/forecast`, `/key`, `/status`). There is no route that registers a station. To build:

1. `POST /v1/stations` (register: returns a station id and a key once), `GET /v1/stations`, `GET /v1/stations/{id}`, `POST /v1/stations/{id}/rotate-key`, and `POST /v1/stations/{id}/readings`, which the draft contract in `nyuchi/stationkit` issue 5 already specifies.
2. A registered station carries a Places id (`placeId`), an owner entity and a WIGOS id where it has one, and stores no country or province. `weather.stations` already has `placeId` and `ownerEntityId` fields, so this follows the shape in use.
3. Move ingest onto the same key model so Weather Underground and Ecowitt uploads (today `weather-ingest.nyuchi.com`, the `mukoko-weather-stations` Worker) authenticate against stations registered through the API.
4. The weather Worker stops being a second registry. Its register route (`/api/py/stations/register` today) is retired once the API's exists.

## 6a. A new source of ground truth: Zimbabwe's WIS2 feed

The Meteorological Services Department (MSD) publishes hourly surface observations from its automatic stations through an open, keyless OGC API under WMO's core data policy (free and unrestricted exchange). Read from the live node on 2026-10-29 (brief of the same date). This is the strongest ground truth available for Zimbabwe, and it plugs into what exists: `weather.stations` (registry), `weather.stationObservations` (raw hourly), then the existing fusion into `weather.observations`. It needs no new collection.

What the first look found:

- **19 stations are registered; four reported in the last 15 days** (Bulawayo Goetz, Victoria Falls, Buffalo Range, Mount Darwin). Registered does not mean publishing. Buffalo Range had been silent about 20 hours.
- **Rainfall was exactly 0.0 in all 833 reported hours at every reporting station.** That may be a dry fortnight, but zero everywhere for 16 days is unusual enough to verify. Hold this feed's rainfall out of farm advice until MSD or a cross-check (CHIRPS) confirms the gauges.
- **Quirks that break a naive import:** one row per parameter per station per hour, so group by `reportId` (precipitation carries an interval, the rest an instant); wind speed is m/s, so km/h is x 3.6; pressure is station-level, not sea-level; and some stations have doubtful coordinates or elevations (Beitbridge's published point is near Harare, Nyanga's elevation and barometer height differ by about 360 m, and Kutsaga is registered twice).
- **Import rules:** idempotent upserts keyed `wis2:<reportId>`; attribution "Meteorological Services Department of Zimbabwe, via WMO WIS2" on every record; flag questionable values, do not fix them; never invent a station that is not in the registry; keep `lastObservedAt` honest so the app can show a station as stale.

This feeds Objective 4 directly: it is the observation set the forecast verification join needs, and a model for registering stations on the Nyuchi API (a WIGOS id and a Places id on each station). Open decisions from the brief (D1 to D8): which `metrics` naming family the app reads, where the WIGOS id lives, station versus sea-level pressure, province assignment by polygon (provinces are centroids today), how official data ranks against community data in fusion, an MSD record in `entity.entities`, and rainfall trust. The reference code in the brief was run against the live API.

### SAAOPA WX-CoPilot: a second live feed

`wx.saaopa.org` is a community weather site ("WX-CoPilot", run under SAAOPA, saaopa.org). Its page is a script-driven app; the API it calls is `wx-api.saaopa.org`. Read on 2026-10-29 from the public routes only (`/stations`, `/stations/status`, `/stations/{code}`, `/metar/{code}`; the `admin` routes need a login and were not touched):

- **84 stations:** 25 automatic weather stations (`aws`, all reporting, about 8 minutes old), 57 official aerodromes and 2 webcams. 34 are in Zimbabwe, then South Africa (16), Mozambique (12), Botswana (10), Namibia (7) and Zambia (5).
- **Live fields:** temperature, dew point, wind direction, wind speed and gust (knots) and QNH, about every 10 minutes. No rainfall in the status route.
- **No stated terms.** There is no OpenAPI document, no licence and no operator named on the page. Ask SAAOPA for permission and attribution wording before any scheduled call. The parsers exist; nothing calls the API.
- **Do not duplicate:** the 57 official aerodromes republish METARs we can read from the Aviation Weather Center. Ingest the 25 `aws` stations only.
- **QNH is not station pressure.** It is kept as its own value, never written to the station-pressure metric.

The parsers for this feed and for the MSD WIS2 feed are `weather_core::external_feeds` (`mukoko-dev/mukoko-weather#362`); the plan, the gates and what is not built are in `mukoko-dev/mukoko-weather#361`. A WIS2 page boundary can cut a station-hour in two (seen live), so a writer must merge per metric, never replace.

## 6b. Tooling gaps found while building the agriculture database

From the same session (brief of 2026-10-29; items marked tested were run, the rest come from the tools' own descriptions):

1. **No validator or schema contract in the Nyuchi Data tool.** It shows that a collection exists, its counts and indexes, but not its required fields, enums or `validationAction`. The `knowledge.topics` inserts failed twice with only "Document failed validation". Request: a read-only collection-info tool that returns validators, collection options and the declared schema from `data-infra`.
2. **The Atlas tool is write-capable and has no scoping.** It accepted writes across the cluster (stopped only by a validator), takes optional filters on update and delete, and bundles cluster and database-user administration with data tools. Use a dedicated least-privilege database user per task.
3. **Index reporting has two defects:** `_id_` shows as not unique, and compound index key order is lost. Unique, TTL and partial indexes cannot be created through the Atlas tool at all.
4. **No read-only aggregation**, so verifying a load needs the write-capable tool.
5. **Operational honesty:** 24 of 63 Nyuchi Data tools front stores that are undeployed, unconfigured or empty (Postgres undeployed, Redpanda and Cassandra unconfigured, Doris empty).

Practical rules until fixed: load only small curated data through a tool, verify with an aggregate checksum, give every document a `loadId` so a rollback is one filtered delete, and use a script with a scoped connection string for anything larger. These sit with the `data-infra` team.
