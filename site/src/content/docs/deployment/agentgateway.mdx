[`nyuchi/agentgateway`](https://github.com/nyuchi/agentgateway) is the agent
gateway all Nyuchi agents route through. It runs the
[agentgateway](https://agentgateway.dev) Docker image and ships to Vercel
using Vercel's [container image support](https://vercel.com/docs/functions/container-images) —
a `Dockerfile.vercel` at the repo root deploys straight to a Vercel Function,
no separate container host needed.

Live at **`mcp.nyuchi.com`**.

## Why Vercel, not a standalone Docker host

Vercel Functions can now run OCI-compatible container images directly: a
`Dockerfile.vercel` (or `Containerfile.vercel`) at the project root is
auto-detected, built, and pushed to the Vercel Container Registry on deploy.
Functions scale to zero and bill on **Active CPU** — only while the container
is actually handling a request — which fits a gateway that mostly idles
between agent calls. `vercel dev` builds and runs the same image locally
(needs the `docker` CLI and daemon).

## Repo layout

| File | Does |
| --- | --- |
| `Dockerfile.vercel` | `FROM cr.agentgateway.dev/agentgateway:v1.4.1`, copies in `config.yaml`, runs `agentgateway -f /config.yaml` |
| `config.yaml` | Gateway listener config — currently just the proxy port. Routes/backends for individual agents land here as they come online |
| `vercel.json` | Sets `PORT=3000` |

```docker filename="Dockerfile.vercel"
FROM cr.agentgateway.dev/agentgateway:v1.4.1

COPY config.yaml /config.yaml

CMD ["-f", "/config.yaml"]
```

## Port resolution

A Vercel Function running a container image forwards traffic to a single
port — `80` by default, overridable with the `PORT` environment variable.
agentgateway's own default gateway listener is `3000`, so `vercel.json` pins
`PORT` to `3000` to match:

```json filename="vercel.json"
{
  "env": {
    "PORT": "3000"
  }
}
```

The admin UI (normally `15000`) has **no bind address in `config.yaml`**, so
it's simply not reachable — Vercel only forwards the one port anyway, and
this matches agentgateway's own default of keeping the admin UI
localhost-only unless `ADMIN_ADDR` is explicitly set.

<Aside type="note">
  agentgateway's standalone Docker docs describe running the admin UI over
  `ADMIN_ADDR=0.0.0.0:15000` for local inspection. Don't set that in the
  Vercel deployment — there's no way to reach a second port on a Function,
  and there's no reason to widen the admin surface for a hosted deploy.
</Aside>

## Deploying

The `nyuchi/agentgateway` Vercel project (team `nyuchi`) was created with
`vercel link` and deployed with `vercel deploy --prod` — it is **not
Git-connected**, so a push to the repo does not trigger a build. Redeploy by
hand:

```sh
vercel link --scope nyuchi --project agentgateway   # once, per checkout
vercel deploy --prod --scope nyuchi
```

Vercel rebuilds and re-pushes the image to the Vercel Container Registry on
every deploy that touches `Dockerfile.vercel` or the files it `COPY`s.
Connecting the GitHub repo (Vercel dashboard → Settings → Git) would make
this automatic on push — not done yet.

### Domain

`mcp.nyuchi.com` is a `CNAME` to `cname.vercel-dns.com` in the `nyuchi.com`
Cloudflare zone (DNS-only, not proxied — Vercel terminates TLS and issues its
own certificate for the domain). Added to the project with:

```sh
curl -X POST "https://api.vercel.com/v10/projects/agentgateway/domains?teamId=<team id>" \
  -H "Authorization: Bearer $VERCEL_TOKEN" \
  -d '{"name":"mcp.nyuchi.com"}'
```

## Limits worth knowing

- **Secure Compute and Static IPs don't work with custom container images
  yet.** Don't route anything through this gateway that assumes a fixed
  egress IP.
- **Scale-to-zero**: an instance with no traffic for 5 minutes in production
  (30 seconds in preview) is torn down. A scaled-down instance gets
  `SIGTERM` with a 30-second grace period before a hard kill.
- **One process, one port.** agentgateway's own multi-port model (proxy +
  MCP + admin) collapses to whatever `config.yaml` binds to the single port
  Vercel forwards — there's no way to expose a second port from the same
  Function.
