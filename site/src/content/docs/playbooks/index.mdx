## Operations playbooks

Procedures, not narrative: how the orchestrator, its sub agents and any human run the Nyuchi, Bundu and Mzizi estate. Written 2026-11-28 from procedures established the hard way. Every command was checked against a real repo; where a procedure depends on a repo-specific file, the file is named. Where a page here and a repo's own `AGENTS.md` disagree, the repo wins. Rules that live elsewhere are linked, not copied: the [Engineering guide](/engineering/guide/), [Contributing](/engineering/contributing/) and, for the Mzizi build loops (authoring, change, progress, freshness), the [Mzizi playbook](https://github.com/mzizi-dev/mzizi-docs/blob/main/playbook.mdx).

No secret, token value, personal datum, private hostname or IP belongs in these pages or in any PR, issue or chat. Name a secret, never show it.

## Adding a playbook

All playbooks live in this section, one page per subject or procedure. To add one:

1. Create `site/src/content/docs/playbooks/<slug>.md` (or `.mdx`) with `title`, `description` and, if the label should be shorter, `sidebar.label`.
2. Add the slug to the Playbooks group in `site/astro.config.mjs`.
3. Add a row to the right table on this page.
4. Add a `## [Unreleased]` entry to `CHANGELOG.md`.

Do not start a new top-level section for a playbook.

## Where the structure lives

The playbooks say how we decide. The structure of the data and the standards we adopt and publish live in [`bundu-labs/bundu-standards`](https://github.com/bundu-labs/bundu-standards): `register/` for standards we adopt, `standards/` for the ones we publish. The canonical model moves there too. A playbook links to a standard by its register id and never restates it.

## Rules for the playbooks themselves

1. A decision names its source (an owner message with its date, a repository file, an issue).
2. "Decided, not built" is said wherever that is the case.
3. No counts of live things in prose; they go stale. Say how to measure them.
4. A playbook for a product (weather, news) follows these and does not restate them.
5. Each playbook says when it was last reviewed. A review reads the repositories, the open pull requests and the live inventory again, and says what it could not verify.
6. Where two written rules conflict, the playbook lists both under "Open for the owner" and does not choose.
