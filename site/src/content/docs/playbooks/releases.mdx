This playbook decides how work is merged and released. Sources: the org `AGENTS.md` and `CONTRIBUTING.md` as proposed in `nyuchi/nyuchi-docs#118` (not merged when this was written), the repositories' own workflow files, and owner messages as dated below. Reviewed 2026-11-17; the red-or-orange rule and follow-through added the same day. Rewritten for trunk-based releases 2026-11-23: there is no `staging` branch (checked that day on nyuchi-docs, nyuchi-api, bundu-docs, bundu-standards, mzizi-docs, mzizi-registry, shamwari and siafudb), and Bundu Docs describes the same flow in [How a change gets released](https://docs.bundu.org/bundu/engineering/releases/how-a-change-is-released/). "Decided, not built" is said wherever that is the case, and where two sources disagree the conflict is listed under [Open for the owner](#open-for-the-owner), not settled here.

## The decisions

1. **Trunk only: `main` is the only target** (owner, 2026-11-23: "We use trunks now. Main is the only target", "there is no staging"). Every PR goes into the default branch. There is no `staging` branch and there should not be one. This replaces the 2026-10-04 rule (`nyuchi/.github#80`) that made `staging` a patch and `staging` to the default branch a minor.
2. **The PR title decides the bump.** Titles are Conventional Commits. When the release job tags a new tip of the default branch, any `feat` in the PRs since the last tag makes the next minor; otherwise the next patch. A breaking change (`type!:`) is refused by the job, and a person releases it as a major; agents never release a major. Minor and patch have no cap and versions compare as numbers. A repository whose version lives in a file sets it to the next allowed version, and CI refuses anything else.
3. **The release is the app's job, not the author's.** `bundu-release[bot]` (the enterprise-owned `bundu-release` GitHub App, whose key lives only in the `org-release` environment) checks the default branch every 15 minutes from `auto-release.yml`; if its tip is not tagged, it tags it `vX.Y.Z` and publishes the release. A repository can opt out with `AUTO_RELEASE=off`. Tagging and the GitHub release are done by the reusable `auto-tag` workflow.
4. **Owner direction, 2026-11-15 and 2026-11-23:** "you have full authority to keep on merging for patches, hot fixes and minor bumps. You can automatically deployed you do not need me", and "keep releasing". So an agent the owner has authorised merges feature and fix PRs into the default branch when the merge gate is met. If a merge queue is slowing a change down, merge it as soon as it is green (owner, 2026-11-23); never bypass a failing or pending check to do so.
5. **The merge gate.** Merge only when the work is complete, CI is green, it is verified at runtime where that is possible, and a code review has run with its findings resolved.
6. **Nothing merges while anything is red or orange** (owner, 2026-11-17: "A merge should be block if anything is red or orange"). Red is a failure, error, cancellation or timeout; orange is anything still pending, neutral or waiting on action. Skipped counts as green. The rule covers every check and status on the commit, required or not. An agent never enables auto-merge or merges while one is red or orange, and never skips or disables a check to get past it. The `All checks green` workflow enforces it: it waits for every other check and status, then fails on anything not green, and making it the required check makes every check behind it required too. Built in `bundu-labs/marketing` (`#215`, `#214`) and `siafuDB/cell`; making it required on the default branch is an owner step, and the other repositories are still to follow.
7. **Land through the merge queue.** Required checks must trigger on `merge_group:`. Use `gh pr merge --squash --auto`, never `--admin`, never a loop of merge calls; treat a 5xx or "merge already in progress" as wait. Do not require a branch to be up to date.
8. **Never close a conflicting PR.** Merge the base into the head, keep every feature, then validate and push. Never rewrite history on someone else's branch.
9. **Nothing reaches the default branch except through a pull request** with its checks green. There is no forward-porting any more: with no `staging`, there is nothing to port to.
10. **Every PR names its issue.** `Closes #n`, `Refs #n` or `No issue: <reason>`. Bot PRs are exempt. A `Closes` closes the issue when the PR merges. Big work gets an issue in the repository that owns it (see the [Platform playbook](/playbooks/platform/)).
11. **Shared workflows are pinned estate-wide at one commit SHA** with a `# vX.Y.Z` comment. Actions are pinned by their full 40-character SHA. Dependabot targets the default branch and waits seven days before proposing a new version (a Semgrep rule requires it).
12. **Deploys run on every push to the default branch.** No variable decides whether they run, and a missing secret fails the deploy loudly. See the Edge and secrets section of the [Platform playbook](/playbooks/platform/#edge-and-secrets).
13. **A change is not done until it is released.** For the weather repository, a release also needs a plain-language note in its releases page, written for the person using the app: no PR numbers, no code or model names.
14. **Follow every change all the way through** (owner, 2026-11-17). Each change merges into the default branch and is deployed and released on its own; do not wait for several PRs to batch up. The checks on the PR and in the merge queue are the checkpoint (does it build and work with the rest of the app); the deploy is followed by a final check against production. Nothing is left as a draft.

## How to ship a change

1. Open or update the issue. Branch from the default branch. Open a draft PR into it that names the issue.
2. Run the repository's own checks locally first (format, lint, typecheck, tests for what you changed). A push that turns CI red costs a cycle.
3. When the PR is ready and every check and status is green (none red or orange, required or not), enable auto-merge and let the queue land it; if the queue is slow and everything is green, merge it. Watch CI and the deploy after the merge: a red default branch blocks the release.
4. Leave the tag to the app. It tags the new tip within 15 minutes and picks the bump from the PR titles.

## Open for the owner

These are conflicts between written rules. A playbook cannot choose between them.

- **Merge commit or squash for the release PR.** The org `AGENTS.md` in `#118` says to promote with a merge commit and never squash, because a squash release erased work on 2026-10-21. The org `CONTRIBUTING.md` in the same PR says squash or rebase, linear history, merge commits disabled. The older rule of 2026-10-21 says squash only, through the queue. The bot's release PRs say auto-merge with a merge commit, and merge commits exist on default branches. `nyuchi/nyuchi-api#524` records that its `merge-queue-main` ruleset uses a merge method, so every release there needed a hand-applied `forward-ported` label. This page's `conventions/overview` stub still says "Never squash on merge".
- **Two release mechanisms in one repository.** `nyuchi/nyuchi-api` has its own `release-pr` and tagging workflows beside the app, and its own release PR was open and conflicted when this was written. `super-app-web` has a `release-pr` workflow and does not use the bot lane. Which wins, per repository, is not written down.
- **Who may deploy.** The org rule is every push to the default branch. `super-app-web` deploys by hand only (owner, 2026-10-08). `nyuchi-docs` deploys through Cloudflare Workers Builds on merge. The Vercel apps deploy on push.
- **What the app announces and whether it tags itself** is not visible from the repositories; the `nyuchi/.github` workflows were not readable when this was written.
- **A check named "no agent-local files"** exists on the weather repository, but no workflow carrying that text was found in the others. Some repositories track `CLAUDE.md` and some keep it untracked so the default branch never ships it. One rule is needed.
