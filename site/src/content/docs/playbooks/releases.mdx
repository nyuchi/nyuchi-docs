This playbook decides how work is merged and released. Sources: the org `AGENTS.md` and `CONTRIBUTING.md` as proposed in `nyuchi/nyuchi-docs#118` (not merged when this was written), the repositories' own workflow files, and owner messages as dated below. Reviewed 2026-11-17. "Decided, not built" is said wherever that is the case, and where two sources disagree the conflict is listed under [Open for the owner](#open-for-the-owner), not settled here.

## The decisions

1. **The branch decides the bump** (owner, 2026-10-04, `nyuchi/.github#80`). A merge into `staging` is the next patch. A release from `staging` to the default branch is the next minor. A major is made by hand only, with the `semver:major` label or `bump: major`; agents never release a major. Minor and patch have no cap and versions compare as numbers. A repository whose version lives in a file sets it to the next allowed version, and CI refuses anything else.
2. **Feature and fix PRs go into `staging`; `staging` to the default branch is a release** (the same rule). Open a draft PR first, with Conventional Commits titles.
3. **The release PR is the app's job, not the author's.** `bundu-release[bot]` (the enterprise-owned `bundu-release` GitHub App, whose key lives only in the `org-release` environment) opens the `staging` to default-branch PR and turns auto-merge on, from `auto-release.yml`, on a 15-minute schedule. A repository can opt out with `AUTO_RELEASE=off`. Tagging and the GitHub release are done by the reusable `auto-tag` workflow.
4. **Owner direction, 2026-11-15, for the weather work:** "We are not releasing a V1 yet so you have full authority to keep on merging for patches, hot fixes and minor bumps. You can automatically deployed you do not need me." Then, once the app existed: "It's just staging to main." So an agent the owner has authorised merges feature and fix PRs into `staging` when the merge gate is met, and never merges or edits a `staging` to default-branch release PR, which the app handles. This is the owner's message to one session, not a repository rule; the org file still says only the owner releases, or an agent the owner has authorised.
5. **The merge gate.** Merge only when the work is complete, CI is green, it is verified at runtime where that is possible, and a code review has run with its findings resolved.
6. **Land through the merge queue.** Required checks must trigger on `merge_group:`. Use `gh pr merge --squash --auto`, never `--admin`, never a loop of merge calls; treat a 5xx or "merge already in progress" as wait. Do not require a branch to be up to date.
7. **Never close a conflicting PR.** Merge the base into the head, keep every feature, then validate and push. Never rewrite history on someone else's branch.
8. **Nothing reaches the default branch outside a release.** A PR into the default branch comes from `staging`, a `release/*` branch, or `bot/registry-pin`. A commit that did reach the default branch must be forward-ported, then labelled `forward-ported`.
9. **Every PR names its issue.** `Closes #n`, `Refs #n` or `No issue: <reason>`. Bot PRs are exempt. A `Closes` in a PR into `staging` closes nothing until the release PR repeats it. Big work gets an issue in the repository that owns it (see the [Platform playbook](/playbooks/platform/)).
10. **Shared workflows are pinned estate-wide at one commit SHA** with a `# vX.Y.Z` comment. Actions are pinned by their full 40-character SHA. Dependabot targets `staging` and waits seven days before proposing a new version (a Semgrep rule requires it).
11. **Deploys run on every push to the default branch.** No variable decides whether they run, and a missing secret fails the deploy loudly. See the Edge and secrets section of the [Platform playbook](/playbooks/platform/#edge-and-secrets).
12. **A change is not done until it is released.** For the weather repository, a release also needs a plain-language note in its releases page, written for the person using the app: no PR numbers, no code or model names.

## How to ship a change

1. Open or update the issue. Branch from `staging`. Open a draft PR into `staging` that names the issue.
2. Run the repository's own checks locally first (format, lint, typecheck, tests for what you changed). A push that turns CI red costs a cycle.
3. When the PR is ready and green, enable squash auto-merge and let the queue land it. Watch CI after the merge: a red `staging` blocks the release.
4. Leave the release PR alone. If it is conflicted or red, fix the cause on `staging`; the app re-opens it.

## Open for the owner

These are conflicts between written rules. A playbook cannot choose between them.

- **Merge commit or squash for the release PR.** The org `AGENTS.md` in `#118` says to promote with a merge commit and never squash, because a squash release erased work on 2026-10-21. The org `CONTRIBUTING.md` in the same PR says squash or rebase, linear history, merge commits disabled. The older rule of 2026-10-21 says squash only, through the queue. The bot's release PRs say auto-merge with a merge commit, and merge commits exist on default branches. `nyuchi/nyuchi-api#524` records that its `merge-queue-main` ruleset uses a merge method, so every release there needed a hand-applied `forward-ported` label. This page's `conventions/overview` stub still says "Never squash on merge".
- **Two release mechanisms in one repository.** `nyuchi/nyuchi-api` has its own `release-pr` and tagging workflows beside the app, and its own release PR was open and conflicted when this was written. `super-app-web` has a `release-pr` workflow and does not use the bot lane. Which wins, per repository, is not written down.
- **Who may deploy.** The org rule is every push to the default branch. `super-app-web` deploys by hand only (owner, 2026-10-08). `nyuchi-docs` deploys through Cloudflare Workers Builds on merge. The Vercel apps deploy on push.
- **What the app announces and whether it tags itself** is not visible from the repositories; the `nyuchi/.github` workflows were not readable when this was written.
- **A check named "no agent-local files"** exists on the weather repository, but no workflow carrying that text was found in the others. Some repositories track `CLAUDE.md` and some keep it untracked so the default branch never ships it. One rule is needed.
