This playbook decides how we build APIs. Sources: the `AGENTS.md` files of `nyuchi/nyuchi-servers-api` and `nyuchi/data-infra`, `docs/event-platform.md`, `docs/ledger-key-contract.md` and the weather repository's `CLAUDE.md`; since the review of 2026-11-17, `docs/architecture/rust-routing.md` and `data-access.md` in `nyuchi/nyuchi-api` (formerly `nyuchi/api-gateway`) and the owner's messages on `nyuchi-api#547`.

## The decisions

1. **Four gateways, four jobs.** Mzizi API (public), Nyuchi API (B2B, `api.nyuchi.com`), Mukoko API (consumer), Nyuchi Servers API (internal, no public IP). The Nyuchi API validates actions and is where places and stations are created. Where a write lands follows the [Data playbook](/playbooks/data/): documents in MongoDB, relational and money in the ledger.
2. **Callers integrate through the contract.** `GET /openapi.json` (OpenAPI 3.1) is the contract. Callers never import our code. A route is added to the route table, the router and the OpenAPI document together.
3. **Every error is RFC 9457 Problem Details**, with `instance` and `traceId`, rendered in one place. Never write an error body by hand.
4. **Standard auth and discovery.** OAuth 2.1 and OIDC, with RFC 9728 protected-resource metadata. Internal `nyk_` keys are a second factor, not an identity. Keys are stored as digests in the ledger, never in Mongo.
5. **Standard observability and limits.** W3C Trace Context and OpenTelemetry; IETF RateLimit headers; per-key limits and usage metered in the ledger.
6. **JSON conventions.** Field names are camelCase, timestamps are RFC 3339 UTC, countries are ISO 3166, currencies ISO 4217, languages BCP 47. Events are CloudEvents.
7. **Read your write.** An action returns the new state itself, not from a view that may not have caught up.
8. **Public data endpoints say how fresh they are.** An answer that comes from a cache or a fallback says so (`X-Cache`, `X-Weather-Provider` are the pattern in weather), and a degraded answer is not cached as if it were whole.
9. **Be a good neighbour to providers.** Budget calls to free upstreams, cache, and fail to a clearly labelled fallback. Never hammer a community source: ask permission and for attribution wording first (the SAAOPA rule in the weather playbook).
10. **Weather API.** `/v1/weather` is a Nyuchi API router (`nyuchi-api#397`, an issue, still open). Stations are registered on the Nyuchi API (owner, 2026-10-29), and the owner confirmed on 2026-11-13 that the Nyuchi API builds the station routes and that anonymous registration ends (`mukoko-weather#293`). **Built since 2026-10-29:** the station domain logic, `/v1/stations` (register, list, status, readings, rotate key, claim), the `/v1/stations/service/*` routes for the ingest Worker and an import path, merged to `staging` on 2026-11-13 (`nyuchi-api#540` to `#544`). Not verified: that they are in a tagged release. Per the stationkit console's README, they answer `503 stations_unavailable` until the owner applies the indexes. `api.mukoko.com/v1/weather` is a Worker with Nyuchi API keys and per-key limits (`mukoko-api#19`); the full client cutover is open (`mukoko-api#9`).
11. **The gateway is the only read path for apps** (owner direction, 2026-10-02, `docs/architecture/data-access.md`, status "Proposed"). Apps are thin clients with no database client. Doris answers search and aggregation; MongoDB answers single records, cached; the relational database owns people, entities, memberships and keys; money goes to the ledger. Caching has three layers (the framework cache, an in-process gateway cache with single-flight, and the edge with `Cache-Control: public, s-maxage`); a failure is never cached and a credentialed response is private. When the gateway cannot answer it returns a non-2xx, never an empty 200. Limits are keyed by credential. `mukoko-news` is the first app moving (see the [News playbook](/playbooks/news/)); weather's step is unchecked.
12. **Every backend service reaches data only through the Servers API** (owner direction, 2026-11-13, recorded in the Servers API README). `api.mukoko.com` is the consumer API and is not for internal apps.

## Moving a route to Rust

The Nyuchi API is being ported route by route, with Python as the default answer until a route is proven (rulebook: `docs/architecture/rust-routing.md` and `routing/routes.json` in `nyuchi/nyuchi-api`). Owner direction, 2026-11-13: "Yes to phase 2 move everything over to rust", and 2026-11-14: "start dropping the python routes". What is decided and built:

1. **Two fields per route.** `port` is a claim about the Rust code: `not_started`, then `built` (the route exists and its parity tests run), then `proven` (it matches Python on the same seeded data, against a real `mongod`). `mode` is who answers in production: `python`, `shadow` (Rust is mirrored on a bounded sample and compared, the client still gets Python's answer), then `rust`. A route that is not listed goes to Python.
2. **Shadow needs a built or proven port; rust needs a proven one;** both need a proof file in the repository. A flip is a one-line PR editing `mode`. **Only the owner flips `mode` away from `python`.** Tranche 4 (anything that issues or checks identity, keys or tokens, or moves money) needs the owner's approval per route.
3. **Tranches:** 1 hot public reads, 2 other reads, 3 writes, 4 identity, keys, tokens and money.
4. **`anonymous_only`:** the Rust side answers callers with no credential only; a credentialed request goes straight to Python and is counted.
5. **Rollback is one of three switches:** `mode` back to `python`, the `ROUTER_KILL_SWITCH` Worker variable, or removing the Worker route. The table is compiled into the Worker, so a table change is a deploy.
6. **Parity is byte-checked.** Golden files are written by the Python app and the Rust code must reproduce them; the tranche 2 files record the SHA-256 of the exact body bytes. Writes are never replayed in shadow.
7. **"Proven" means proven on synthetic data on a local database.** Not a live cluster, not under load, not for a credentialed caller. **Nothing is deployed and the router has never run in a Workers runtime** (the rulebook's own status). On 2026-11-17 no route answered from Rust.
8. **Measure the state, do not quote it:** `python scripts/rust_routes.py --summary` prints the progress table; CI runs `--check`.
9. **Decided with the port (owner, 2026-11-13, `nyuchi-api#547`):** Rust adapters copy production's effective 30-second `maxTimeMS`; the related-articles missing `await` is fixed in Python first and that route leaves the port; Doris topics stay in Python and the Rust origin does not reach Doris. The shadow period, the Fly app and every `mode` flip are held for the owner.

## How to add an endpoint

1. Name the domain that owns the data ([Data playbook](/playbooks/data/)) and the standard each field follows.
2. Define the request and response types first; they generate the OpenAPI document.
3. Return problems for every non-2xx.
4. Test the contract: the route table, the router and the OpenAPI document agree.
5. State rate limits and what the endpoint costs per call.
